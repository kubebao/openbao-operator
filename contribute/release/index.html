Prepare a release

Maintainer workflow for requesting, gating, publishing, and verifying an OpenBao Operator release.

Updated 30 October 2026 · 15 min read

The release path qualifies the release-please PR with the full release profile before merge, then creates a signed tag and draft GitHub Release. The tag starts a workflow that rebuilds the tagged commit, requires the qualified image digests and payload bytes, and promotes images by digest to publish the release.

Create release-X.Y from the published X.Y.0 commit. Normal development can then resume on main while patch releases remain narrow.

Prepare the release content

Keep CHANGELOG.md generated by release-please. Put the human summary, upgrade notes, and migration callouts in release-notes/X.Y.Z.md. The tag workflow prepends that file to the generated changelog section when it creates the draft release. Prereleases use their exact version, for example release-notes/X.Y.Z-rc.1.md; do not reuse stable notes whose installation commands reference a version that has not been published yet.

For every stable release, including patches, add website/content/releases/X.Y.Z.md and update the highlighted release and archive in website/content/releases/_index.md. These pages are maintained by hand; the docs build does not generate them from GitHub Releases or CHANGELOG.md. Include the release highlights, upgrade guidance, and links to the published artifacts and applicable migration procedures. Run make docs-build to validate the pages.

When a stable X.Y.0 follows one or more release candidates, release-please generates its new changelog section from the latest release-candidate tag. After release-please creates the stable release PR, replace only that new section with a concise rollup from the previous stable release to X.Y.0. Use the previous stable tag in the comparison link, and keep the incremental release-candidate sections below it. Do not add the stable section before release-please creates the PR because that can produce duplicate version headings.

If the final release candidate contains all user-facing commits, the pinned exact-version wrapper permits release-please to create a stable PR with only the new version heading. Replace that heading-only section with the same reviewed previous-stable rollup before you authorize the release.

For a patch, make the conventional commit or squash title describe the user-visible fix. Release-please uses that text to generate the changelog.

verify

Check release automation locally

devenv test
devenv tasks run operator:bootstrap
devenv tasks run operator:doctor
devenv tasks run operator:ci-core
devenv shell -- make verify-workflows

Also confirm that compatibility guidance, generated API surfaces, and release notes match the candidate. Review current main, Nightly, and performance evidence, and the release PR’s qualification results, before authorizing publication.

Set the previous stable version, target release, and pinned baseline init image in test/fixtures/operator-upgrade/versions.env. Keep the Hardened fixture’s init image consistent with that pin. Add an upgrade section for the target release. Add or update API migration fixtures only when a manifest migration needs coverage, and wire each new fixture into a test. Preserve approved historical migration pairs: the runtime upgrade baseline, the fixture pair, and the schema compatibility baseline are independent. Merge these fixture changes in a normal PR before the release PR; the release PR cannot change tests or fixtures.

CRD_COMPAT_TARGET labels the compatibility report; it does not select a version-named migration fixture. Advancing the release target alone does not require an unused target fixture. Keep the existing 0.5.0-to-0.5.1 operator-upgrade fixture pair and the schema baseline unless a separately reviewed migration changes them.

i

Hugo versions documentation by minor line

next tracks main; the unprefixed site is the latest stable minor line. Before the first X.Y.0 tag, copy the reviewed next contract into X.Y.x, pin its API source to the final tag, and make it the stable default. Archive the previous stable product tree before promotion. Keep release installation commands version-pinned instead of copying the edge installation procedure. Patch releases update that same X.Y.x line and its release notes; they do not create another documentation route. latest remains an alias to stable and never tracks unreleased code.

The release workflow builds the complete Hugo site from the tagged tree and publishes that validated artifact. There is no generated patch-level snapshot command: the reviewed minor-line content must already be in the release change. Normal main Pages runs always build and validate, but publish only when the configured stable version has a published, non-prerelease GitHub release. Missing or draft releases retain the existing live site; unexpected API or configuration errors fail publication. The tagged release deployment remains after artifact promotion.

During preparation, mark unpublished release content and incomplete qualification as pending. Before authorizing publication, replace those preparation notices with the reviewed release status, check the final tagged API source, and include the final release evidence. Do not add future pass claims.

Request an exact version

Release-please opens normal release PRs from conventional commits. Use the Prepare Release-As PR workflow when a prerelease, patch, or other exact version must be requested explicitly.

request

Create an auditable Release-As marker PR

gh workflow run prepare-release-as-pr.yml \
  --repo kubebao/openbao-operator \
  -f target_branch=main \
  -f version=X.Y.Z-rc.1

For a patch, use target_branch=release-X.Y and a version in that release line. The workflow rejects invalid SemVer, missing or mismatched branches, existing tags or releases, open release-please PRs, and conflicting marker state. It creates an empty signed-off commit containing Release-As: <version> on an automation/release-as-* branch.

Merge the marker PR first. Because protected branches require squash merges, the branch-aware Release Please PR workflow validates that the resulting marker commit is empty and recovers the exact version from its generated squash subject. It then opens or updates the actual release PR. The direct release_as dispatch input remains available, but the marker PR is the preferred auditable path.

Review and merge the release PR

Before merge, verify that the release PR updates these surfaces consistently:

  • .release-please-manifest.json and generated CHANGELOG.md;
  • charts/openbao-operator/Chart.yaml version and appVersion;
  • Artifact Hub changes, image metadata, prerelease flag, and security-update flag;
  • release-notes/X.Y.Z.md when the release needs a human summary or upgrade guidance;
  • website/content/releases/X.Y.Z.md and the release index for stable releases.

A release PR may change only release metadata and documentation content: the manifest, CHANGELOG.md, charts/openbao-operator/Chart.yaml, release-notes/, website/content/, website/content-versions/, website/data/, website/hugo.toml, and website/README.md. Merge code, CI, test, fixture, and docs tooling changes in a separate PR first. The workflows, scripts, and tests that qualify the release PR then match the reviewed base branch.

Qualify the release PR

Add the release:candidate label when the release content is complete and the base branch is frozen. After the API checks pass, approve Approve Candidate Publication in the release-candidate environment. This approval authorizes publishing executable candidate images under technical tags in the normal GHCR repositories. It does not authorize stable version tags or a published GitHub Release. The workflow checks the actual environment review history before either image build can write to GHCR.

The Release Candidate workflow runs the full release profile against the PR’s merge commit:

  1. API contract and generated-file checks, govulncheck, and Semgrep;
  2. two independent image builds that use the PR head’s commit time as SOURCE_DATE_EPOCH;
  3. Trivy image scans, the release-gate E2E matrix, and the previous-stable operator upgrade;
  4. image provenance verification and byte reproducibility of the images and release payloads.

The Qualified Release Candidate job runs only after every qualification job passes. The run retains the qualified payloads and image digests as the release-candidate artifact for 30 days.

Each push to the labeled PR, including a release-please update after the base branch moves, starts a new qualification and cancels the previous one. Rerun failed jobs to retry a flaky lane; the rerun qualifies the same head. The workflow rejects a head that is not up to date with its base branch, because the release rebuild must reproduce the qualified tree.

The release PR gate requires the release:ready label, the release PR path rule, and a passed Qualified Release Candidate job for the current head with an environment approval from dc-tec. Every release PR also requires a current-head review from dc-tec; environment approval does not replace PR review. The gate uses scripts from the base commit. If qualification finishes after the gate runs, reapply release:ready to re-evaluate it.

Candidate helpers are keyless-signed by the reusable build workflow. Only the Hardened E2E fixtures opt into the exact reusable-build.yml@refs/pull/N/merge subject and GitHub OIDC issuer. They keep verification enabled with failurePolicy: Block and transparency-log verification. Production defaults and the upgrade fixture’s published baseline policy remain unchanged.

Configure release approvals

Before using these workflows, configure both release-candidate and release-publish environments:

  • Set dc-tec as the required reviewer on both environments.
  • Disable administrator bypass. The scripts require an actual approval in the run’s review history.
  • For release-candidate, disable Prevent self-review and select the branch rule refs/pull/*/merge. The maintainer triggers candidate qualification by adding the label and must be able to approve that run.
  • For release-publish, keep Prevent self-review enabled and retain the existing SemVer tag rules. The release-tag App triggers this workflow, so the maintainer can approve it without self-review.

In these workflows, a missing or unprotected environment fails the approval-history check before registry-write jobs start. Each new PR head needs its own approved qualification run. Failed jobs can reuse authorization for the same immutable run. This check assumes reviewed workflow definitions and enforced required checks; it does not restrict the package permissions of other workflows.

Keep release PRs App-authored. The maintainer can review the release-please App’s PR and approve the release-tag App’s publication run without another maintainer. CODEOWNERS review requirements do not prevent this path. Keep required CI, the release gate, signatures, and tag protections enforced. Any maintainer review exception for ordinary self-authored code PRs must remain separate from these checks and does not replace release PR approval.

These repository settings must be configured separately; committing workflow YAML does not configure reviewers or ruleset exceptions. See environment protection and rulesets. GitHub documents refs/pull/*/merge in deployment branch rules.

After merge, changes to .release-please-manifest.json trigger the Release Tag workflow. The workflow resolves the exact merged release PR, verifies its release files, creates a GPG-signed annotated SemVer tag, and creates or refreshes the matching draft GitHub Release. Chart metadata and changelog edits alone do not trigger release tagging. The tag GitHub App is the only automation identity that should have SemVer tag-ruleset bypass.

Use the manual branch-head tag target to retry an unpublished release after an approved release-branch fix. The branch head must descend from the release PR merge and carry the same release version. Label the fix PR release:candidate and wait for its qualification before merging it; the Release workflow requires the tagged commit to be the squash merge of a qualified PR.

To remove a failed unpublished candidate, dispatch Release Tag with operation=remove-unpublished. Provide its expected_tag_object_sha, expected_commit_sha, and completed failed_run_id. The workflow requires an empty draft or an already removed draft, a matching signed tag, and a failed or cancelled Release run whose promotion job never starts. It checks promotion jobs across all run attempts. The release App removes the draft and tag without changing tag protections. After merging and qualifying the fix, dispatch operation=create with tag_target=branch-head to create the corrected signed tag and draft. Corrections to a published release require a new version.

Let the tag workflow publish

The tag triggers the Release workflow. It does not repeat the release tests. It:

  1. checks that the chart version, app version, tag, and draft release agree;
  2. resolves the PR merged as the tagged commit, requires the same tree as that PR’s head, and finds the head’s Qualified Release Candidate run;
  3. waits for Approve Release Publication in release-publish and verifies the approval history before any tagged rebuild writes to GHCR; this authorizes publication only if the remaining checks pass;
  4. rebuilds the four images from the tag with the qualified SOURCE_DATE_EPOCH, attests them, and verifies that the rebuilt digests carry the qualified PR’s build attestations;
  5. packages the release payloads and requires the qualified image digests and payload bytes;
  6. promotes the verified image manifests by digest, without rebuilding;
  7. signs images and the OCI Helm chart with the tag-scoped workflow identity;
  8. signs and attests checksums, generates SBOMs and provenance-index.json, uploads assets, and publishes the draft GitHub Release.

Publication approval precedes the tagged rebuild and its verification results. Any wait timer on release-publish also delays that rebuild. The automated comparisons must pass before the publishing job promotes version tags, pushes the chart, or publishes the GitHub Release.

Inspect failures before rerunning jobs. Byte or provenance mismatches stop publication even after approval. For transient infrastructure failures, rerun the failed jobs. Promotion accepts existing version tags and chart packages only when they match the verified digests and bytes. Registry authentication, transport, server, and malformed-response errors stop publication. Only an authenticated HTTP 404 with MANIFEST_UNKNOWN permits creating a missing tag or chart. The publishing job replaces draft assets so a rerun after a partial upload publishes one consistent signature set. For an already published GitHub Release, the upload step only confirms the published checksums.

The stable public distribution surface is:

SurfacePublished result
GHCR imagesVersion-tagged, digest-addressable, signed manager, init, backup, and upgrade images
GHCR Helm OCICanonical signed chart at ghcr.io/kubebao/charts/openbao-operator
GitHub ReleaseInstaller manifest, CRDs, policy approval files, checksums and signature bundles, SBOMs, and provenance index
Artifact HubDiscovery and metadata for the GHCR chart

These coordinates apply to releases published under KubeBao. Historical releases, including 0.5.1 and earlier, retain their ghcr.io/dc-tec images and charts, dc-tec/openbao-operator signing identities, and original provenance. Use the repository and signer recorded in each release’s provenance index when verifying historical artifacts. Do not republish a historical version under the new coordinates.

OLM bundles remain repository and CI validation assets; public OperatorHub publication is not part of the supported release procedure.

dist/install.yaml and dist/crds.yaml are generated release outputs. Do not treat local copies as source-controlled publication artifacts.

make build-policy-approvals generates operator-policy-approval.hcl and operator-policy-approval-with-backup.hcl in dist/. Both approve the two supported upgrade strategies; only the second includes backup policy management. The Release workflow generates and compares both files in its reproducibility check, includes them in signed checksums and the provenance index, and uploads them with the release.

Verify the published release

Post-Release Verification runs after a successful Release workflow and can also be dispatched for a tag. It verifies the remote tag, required assets, checksum signature, OCI chart signature, release-please label cleanup, and absence of open or stale release-please branches. It stores JSON evidence for 30 days and adds the evidence link and digest to the release PR.

verify

Run post-release verification

VERSION=X.Y.Z \
REPO=kubebao/openbao-operator \
EVIDENCE_OUT=dist/post-release-verification.json \
hack/ci/verify-post-release.sh

Local verification requires gh, jq, git, Docker Buildx, Helm, and cosign.

For manual workflow runs, select current as the publisher for releases published from the current repository. Select dc-tec/openbao-operator for pre-transfer releases, including 0.5.1. Automatic runs use the current repository as the publisher.

For local verification of a historical release, keep REPO=kubebao/openbao-operator and set PUBLISHER_REPO=dc-tec/openbao-operator. Set EXPECTED_CHART_FILE to the charts/openbao-operator/Chart.yaml extracted from that release’s tag. The verifier reads tags, release assets, and PRs from REPO, but checks signatures, attestations, image paths, and chart paths against PUBLISHER_REPO. It records both repositories in the verification evidence and rejects provenance from a different publisher.

The verifier retrieves image and chart attestations from their OCI registries and checksum provenance from the published checksums.intoto.jsonl asset. This avoids repository-scoped attestation lookup after a repository transfer. Each verification still requires the selected publisher, signer workflow, source ref, artifact digest, GitHub OIDC issuer, and GitHub-hosted runner.

Release-please cleanup checks still apply to the current repository. An open release PR prevents an overall pass even when historical artifact verification succeeds.

Use the provenance index to select digest-pinned subjects for additional checks:

Keep release identities separate

The PR App may create release and marker PRs but must not create SemVer tags. The tag App needs repository contents write and the narrow tag-ruleset bypass, but no PR authority. Rotate their private keys and the dedicated release-tag GPG key independently.

If verification fails or publication state is unexpected, stop and use the publishing incident runbook.

Publish edge Helm charts

Successful main CI builds and verifies an edge chart with version 0.0.0-edge.<run-id>.<attempt>.g<commit>. The fixed 0.0.0 base keeps edge identity independent of release versions. The shared channel workflow compares independent package builds and installs the packaged chart in Kind without image overrides. The edge publisher then pushes those package bytes to ghcr.io/kubebao/charts-edge/openbao-operator, signs the OCI digest, and verifies its GitHub attestation. A publisher rerun accepts an existing chart version only when its bytes match.

The source chart remains shared with releases. Edge packaging sets the operator version and manager digest, and sets helperImages.init, helperImages.backup, and helperImages.upgrade. The controller receives these values as OPERATOR_INIT_IMAGE, OPERATOR_BACKUP_IMAGE, and OPERATOR_UPGRADE_IMAGE. These complete image references take precedence over the repository/version defaults. A cluster’s explicit helper image still takes precedence over the operator default.

The edge repository must remain unregistered in Artifact Hub. Do not publish artifacthub-repo.yml or an Artifact Hub repository registration for it. Stable and release-candidate charts continue to use ghcr.io/kubebao/charts/openbao-operator. Nightly chart publication remains a separate future change and must use a separate unregistered repository too.

On the first publication, check that the new GHCR package permits anonymous pulls and inherits the repository’s Actions access. The edge metadata at edge/latest/metadata.json records the chart reference, version, and digest. The same candidate’s chart archive and checksum are available alongside the manifests on GitHub Pages.

The publisher adds edge-chart-<chart-version> tags to all four image manifests. GHCR housekeeping protects these tags and their reachable platform manifests and signatures. Published charts and these image sets have no automatic expiry. Any future chart cleanup must coordinate chart deletion with removal of the corresponding image retention tags.

Run make verify-edge-chart to check package contents, Helm rendering, reproducibility, and publication retry guards.
