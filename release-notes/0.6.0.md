# OpenBao Operator 0.6.0

OpenBao Operator 0.6.0 adds target-specific controller authentication, guarded
restore recovery, operator-created restore targets, scheduled restore tests,
and administrator-approved policy reconciliation. It also adds IPv6 and
dual-stack networking, Cilium API-server egress configuration, and Azure Key
Vault workload-identity token projection.

This release changes admission for new clusters. Existing clusters keep their
stored authentication mode and data. Review the CREATE and restore changes
before updating CRDs, templates, or automation.

### Controller authentication for new clusters

Every new `OpenBaoCluster` must set:

- `spec.controllerJWTMode: Target`;
- `spec.selfInit.enabled: true`;
- `spec.selfInit.oidc.enabled: true`; and
- a non-empty `spec.selfInit.requests` list.

These requirements apply to both Development and Hardened profiles. OpenBao
initializes itself, configures authentication through the bootstrap requests,
and revokes its bootstrap root token. The operator does not create a root-token
Secret for this initialization path. Configure an independent administrator
login and a usable recovery path before creating the cluster. The updated
samples use this contract.

Deleting and recreating a CR is a new CREATE, even when its name is unchanged.
Update GitOps sources and cluster factories before they create resources. A
recreated CR receives a new UID and controller audience; it does not inherit the
previous object's trust or resource ownership.

Existing CRs with an omitted mode or `Shared` retain Shared authentication on
reads and ordinary updates. The CRD declares no default for the field. An
operator upgrade does not rerun self-init, migrate an OpenBao role, or revoke
an existing root-token Secret. Other admission rules still apply to updates.

### Migrate existing controller trust deliberately

Migration is optional, in place, and one-way. It does not require recreating the
cluster or its storage. Migrate one cluster at a time:

1. Retain administrator access that works independently of the controller JWT.
2. Record the complete existing controller role and its restrictions. Add the
   CR UID audience to that role while preserving subject, policy, issuer, and
   token-lifetime restrictions.
3. Verify a fresh Target JWT can log in through the actual controller
   ServiceAccount and issuer before changing the CR.
4. Set `controllerJWTMode: Target` on the same CR. The existing cluster must
   have self-init and self-init OIDC enabled; this does not replay initialization.
5. Remove shared audience trust. Verify fresh Target login and rejection of the
   shared audience and unrelated target audiences. Revoke or expire previously
   issued OpenBao sessions, accounting for renewable tokens.
6. Take a new snapshot and record the destination trust needed for recovery.

The operator requests short-lived Pod-bound controller credentials for the CR
UID audience. Admission prevents removing Target or changing it to Shared.
Authentication failures require administrator repair; there is no shared-JWT
or root-token fallback. Do not downgrade to an older operator that ignores the
field. Backup, restore, and upgrade executor Job authentication remains separate.

An older snapshot can remove destination trust or restore shared role trust.
Keep an administrator login usable in the restored state. Prepare destination
trust before taking the snapshot, or repair it independently after restoring.
Policy reconciliation does not repair JWT roles.

### Restore authority and recovery

`OpenBaoRestore` becomes an immutable, single-submission request with recorded
execution identity and administrator-controlled recovery.

- API acceptance authorizes one execution. Revoking the submitter's permissions
  does not cancel accepted work; the controller uses its own identity afterward.
- Preparation pins the request and target UIDs, then records Job and executor
  identities. A replacement target does not inherit a prepared execution.
  Referenced credentials remain name-based dependencies; admission does not
  freeze their contents. Use `source.expectedDigest` to pin snapshot bytes.
- Delete the request before execution changes from `Prepared` to `Committed`
  to cancel it. If commitment wins the race, an existing-target or retained
  restore can proceed and deletion is restricted. Deleting a disposable request
  after commitment starts cleanup; it does not prove submission was canceled.
- A committed snapshot submission is not retried or recreated. Deleting a Job
  or restarting the controller does not authorize another attempt.

A restore into an existing cluster ends `Unknown` after submission because
acceptance does not prove that OpenBao finished applying the snapshot. The
restore hold stops operator management; it does not stop client traffic or
fence running processes. Keep traffic stopped while inspecting the outcome.

An administrator must inspect data, restore unseal and authentication access,
and stop or fence remaining executors and old server processes. `Resume` keeps
the hold while the operator restarts voters and read replicas one at a time.
It releases management after the recovery checks and restart finish. An
existing-cluster request remains `Unknown` after this handoff. `Abandon` pauses
the target and hands recovery responsibility to the administrator. Neither
action proves a point-in-time recovery objective or fences an unreachable node.

The release also adds:

- `spec.clusterTemplate` for a new, single-voter OpenBao 2.7.0 or 2.7.1 restore
  target on the same version as the source snapshot. The target requires an
  approved namespace, compatible seal material, destination-local credentials,
  and the asserted source cluster ID and version. The operator does not adopt
  an existing cluster or PVC.
- `Retain` and `Disposable` target lifecycles. Retained targets require trust
  repair and administrator handoff before normal management. Disposable targets
  remove their recorded Kubernetes resources after completion or failure;
  cleanup is not process fencing.
- `spec.backup.restoreTest` for bounded scheduled tests of successful backups
  using disposable targets within one Kubernetes cluster. Cross-cluster
  rehearsals require an administrator-created restore in the recovery cluster.

`OpenBaoCluster.status.restore` is deprecated and no longer written. Use the
restore request's status. `openbao_restore_state` adds recovery values 4–7;
update alerts that assume the earlier value set. An unresolved recovery takes
precedence when the metric is reconstructed from retained requests.

### Backup, policy, networking, and TLS changes

- Backup retention runs as a bounded worker with the successful writer workload's
  identity. Its status is separate from snapshot success. Retention protects the
  current snapshot and a reserved restore-test snapshot; an uncertain worker
  requires inspection rather than automatic resubmission.
- Storage targets accept nested `s3` options with per-field precedence over the
  existing top-level fields. Omitting the nested fields preserves compatibility
  values. Storage clients retain configured private CA trust and handle S3
  credential-Secret regions and complete Azure Blob endpoints consistently.
- `spec.reconcilePolicies` optionally repairs the operator's built-in OpenBao
  policies after an administrator approves the exact policy contents and grants
  the controller role access. Auth methods, JWT roles, approval policies, and
  unrelated policies remain administrator-managed. Use the matching release's
  signed policy-approval file; enabling the CR field alone grants no authority.
- Services and advertised addresses support IPv6 and dual-stack clusters.
  Service primary IP-family changes remain restricted by Kubernetes. The
  operator does not delete and recreate a Service to change its primary family.
- `spec.network.apiServerEgress` can request an operator-owned, namespaced
  Cilium API-server allowance. The platform still owns the CNI and cluster-wide
  policy. Exact caller maps permit approved PVC-binding and helper Pod annotation
  synchronization without granting unrestricted mutation.
- Azure Key Vault seal configuration selects its authentication method and can
  project the workload-identity token directly. The platform must configure
  federation, Key Vault access, DNS, and egress. This does not provision Azure
  infrastructure or qualify every tenant and cloud environment.
- OpenBao 2.7 uses native mounted-certificate reload. Listener configuration
  changes still require restarts. Optional hybrid post-quantum TLS key exchange
  requires OpenBao 2.7 and compatible clients; it does not make certificate
  authentication or every cluster connection post-quantum.
- Raw self-init requests can project selected same-namespace Secret keys.
  Admission checks the submitter's access; the controller does not gain broad
  Secret-read permission. Bootstrap request references remain immutable.

Security checks now compare installed admission specifications with embedded
release contracts. Installed annotations do not establish trust. Tenant
onboarding verifies current binding and ServiceAccount identity. Install matching
policies, bindings, RBAC, and manager settings together; custom installation
identities and external Pod Security label ownership must remain consistent.

### Upgrade from 0.5.3

1. Rehearse the exact platform, OpenBao version, seal, storage, and networking
   combination in staging. Preserve usable independent administrator and seal
   access. Take and verify a current snapshot for each managed cluster.
2. Finish active backups, retention, restores, restore tests, and OpenBao
   upgrades. Do not carry an old restore executor across the operator upgrade.
3. Update templates that create clusters to the Target/self-init OIDC contract.
   Preserve existing omitted or Shared modes unless undertaking the separate
   administrator-prepared migration.
4. Review policy-reconciliation grants, restore alerts, custom installation
   identities, admission caller maps, and externally managed Pod Security labels.
   Plan the new restore acknowledgement workflow before an incident.
5. After publication, verify the 0.6.0 chart, images, CRDs, checksums, signatures,
   provenance, and policy-approval files. Mirror that verified set if required.
6. Apply the verified release CRDs, then upgrade the matching Helm installation.
   Replace the release name and namespace if your installation uses other values.

   ```sh
   kubectl apply -f \
     https://github.com/kubebao/openbao-operator/releases/download/0.6.0/crds.yaml

   helm upgrade openbao-operator \
     oci://ghcr.io/kubebao/charts/openbao-operator \
     --version 0.6.0 \
     --namespace openbao-operator-system \
     --reuse-values \
     --set-string image.repository=ghcr.io/kubebao/openbao-operator \
     --set-string image.tag=0.6.0 \
     --set-string image.digest= \
     --set-string operatorVersion=0.6.0 \
     --wait
   ```

   Helm does not upgrade existing CRDs. The chart upgrades the matching policies,
   RBAC, and manager workloads. Review retained Helm values before using
   `--reuse-values`; change helper image overrides and mirrored repositories to
   the matching verified release references. Cluster-level helper overrides must
   also be updated deliberately. Do not mix a new manager with old executors.
7. Verify controller and provisioner readiness, admission health, tenant
   onboarding, and each managed cluster's health. Confirm that existing cluster
   UIDs, data PVCs, authentication mode, and bootstrap Secret custody remain
   intact. Existing root-token Secrets are not revoked by this upgrade.
8. Verify the init image of every OpenBao Pod and the images of new lifecycle
   Jobs. Existing Pods retain helper binaries from their previous init container
   until replaced. A successful Helm `--wait` does not prove replacement.
   BlueGreen voter StatefulSets use `OnDelete`; a template change alone does not
   replace their Pods. Use the planned maintenance procedure to replace one Pod
   at a time, preserve quorum, and wait for health after every replacement.

For older installations, apply the 0.5.1, 0.5.2, and 0.5.3 migration guidance in
order before this minor upgrade. Routine operator or OpenBao downgrades are
unsupported; prefer a forward fix or a separately rehearsed recovery procedure.

### Custody and qualification boundaries

`deletionPolicy: Retain` keeps operator-owned data PVCs and releases the cluster's
owner references from generated unseal-key and root-token Secrets when present.
New self-init clusters have no root-token Secret to retain. Referenced user
credentials and TLS Secrets follow their own ownership policies. Retained
material remains sensitive recovery data; inventory it and control access.
`DeleteAll` does not remove external snapshot objects.

Release qualification exercises Kubernetes 1.34.3, 1.35.1, and 1.36.1 with
OpenBao 2.6.4 and selected OpenBao 2.7.1 scenarios. The evidence covers the tested
combinations. It does not qualify every distribution, cloud authentication
method, seal, storage driver, or topology. Validate the production combination
in staging and verify the matching published artifacts before installation.

Cilium native routing remains unqualified. VXLAN test coverage does not qualify
native-routing deployments, other CNIs, cloud load balancers, or a different
storage-driver and cloud-identity combination. Validate each production topology
in staging.

The production BlueGreen compatibility policy is unchanged. Pre-2.6 to
2.6-or-newer BlueGreen transitions remain blocked even where an upstream
forwarding fix exists. Switch a healthy, idle cluster to `RollingUpdate`, wait
for the accepted strategy, and then upgrade. A forwarding fix does not prove
mixed-version safety or datastore downgrade compatibility.

The scheduled-backup initialization, AKS/CSI PVC admission, restore snapshot
staging and no-retry corrections from 0.5.2, and Go 1.27.3 certificate protections
from 0.5.3 are carried forward. They are not new fixes first delivered in 0.6.0.
The operator release does not update the separate OpenBao server image.
