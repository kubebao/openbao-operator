### Controller authentication for new clusters

New OpenBaoCluster resources must set `spec.controllerJWTMode: Target`,
`spec.selfInit.enabled: true`, and `spec.selfInit.oidc.enabled: true`. Both
Development and Hardened profiles require a non-empty self-init request list.
OpenBao initializes itself and revokes its bootstrap root token. Configure a
usable administrator login and its recovery path in the bootstrap requests.
Standard initialization and Shared mode remain compatibility paths for existing
resources.

This changes CREATE admission. Update templates, automation, and GitOps sources
before creating clusters with 0.6.0. Deleting and recreating a resource also uses
the new requirements. Install the matching CRDs, policies, RBAC, and operator;
Helm upgrades do not update existing CRDs.

Existing resources with an omitted mode or `Shared` keep their authentication
on reads and ordinary updates. No CRD default changes their stored or effective
mode. Upgrading does not rerun self-init or revoke an existing root-token Secret.

Migration to Target is optional and does not require recreating the cluster or
storage. Prepare the existing OpenBao controller role to accept the CR UID
audience, verify a fresh Target login through the actual controller identity,
and then change the mode. Remove shared audience trust and verify rejection of
shared and unrelated target credentials. Revoke or expire old OpenBao sessions.
Admission prevents removing Target or downgrading to Shared afterward. Repair
authentication through independent administrator access; there is no fallback.

Older snapshots can restore shared role trust or omit the destination audience.
Retain usable administrator access in the restored state and verify audience
restrictions after recovery. Executor Job authentication is unchanged.
