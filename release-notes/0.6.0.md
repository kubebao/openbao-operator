# OpenBao Operator 0.6.0

OpenBao Operator 0.6.0 adds target-specific controller authentication, administrator-controlled restore recovery, operator-created restore targets, and scheduled restore tests. It also adds approved-policy reconciliation, vCluster compatibility improvements, IPv6 and dual-stack networking, and Azure Key Vault workload-identity token projection.

These notes describe the changes when upgrading from **0.5.3**. Review the new-cluster and restore requirements before upgrading.

## Breaking change: authentication for new clusters

Every new Development or Hardened `OpenBaoCluster` must configure:

- `spec.controllerJWTMode: Target`
- `spec.selfInit.enabled: true`
- `spec.selfInit.oidc.enabled: true`
- A non-empty `spec.selfInit.requests` list

Target mode uses short-lived controller credentials with an audience derived from the cluster’s UID. OpenBao initializes itself through the configured bootstrap requests and revokes its bootstrap root token. The operator does not create a root-token Secret for this initialization path.

Configure an independent administrator login and usable recovery access before creating the cluster. Update GitOps templates and cluster factories before they create resources. Deleting and recreating an object is a new CREATE, even when its name stays the same.

**Existing objects with an omitted mode or `Shared` retain their authentication behavior on reads and ordinary updates.** The CRD does not default the field. An operator upgrade does not migrate roles, replay initialization, or revoke existing root-token Secrets.

Migration remains optional. Eligible existing clusters can migrate in place after an administrator prepares and verifies the existing OpenBao role. Migration requires self-init OIDC and preserves the role’s existing restrictions. After switching, remove shared audience trust and revoke or expire previously issued sessions.

The change to Target is one-way. Authentication failures require administrator repair; there is no shared-JWT or root-token fallback.

## Restore execution and administrator recovery

Restore intent is immutable, and each accepted `OpenBaoRestore` authorizes one execution. Revoking the submitter’s permissions does not cancel accepted work. Cancellation must happen before execution commitment.

A committed snapshot submission is not retried or recreated after a controller restart or missing Job.

A restore into an existing cluster ends `Unknown` after submission because submission does not prove that OpenBao finished applying the snapshot. The operator retains a management hold while an administrator inspects the outcome.

The hold does not stop client traffic or fence running processes. Administrators must control traffic, inspect restored data, recover unseal and authentication access, and stop or fence remaining executors and old server processes. They can then acknowledge:

- **`Resume`** to complete recovery checks and a controlled restart before operator management resumes.
- **`Abandon`** to pause the target and retain responsibility for manual recovery.

An existing-target restore remains `Unknown` after this handoff.

### New restore targets and scheduled tests

`OpenBaoRestore.spec.clusterTemplate` can provision a new single-voter OpenBao 2.7.0 or 2.7.1 target on the same version as the source snapshot. The target requires an approved namespace, compatible seal material, destination credentials, and the asserted source cluster identity and version. It does not adopt existing clusters or PVCs.

Targets support two lifecycles:

- **`Retain`** preserves the target for administrator inspection, trust repair, and handoff.
- **`Disposable`** removes the recorded Kubernetes resources after completion or failure. Cleanup does not fence processes.

`OpenBaoCluster.spec.backup.restoreTest` schedules bounded tests of successful backups through disposable targets within one Kubernetes cluster. Cross-cluster rehearsals require an administrator-created restore in the recovery cluster.

Snapshots can restore older authentication configuration. Preserve administrator access that works in the restored state and repair destination JWT trust when necessary. Policy reconciliation does not repair JWT roles.

## vCluster compatibility and namespace cleanup

The release improves vCluster integration while keeping admission protections enabled:

- **PVC binding synchronization:** an opt-in allowance permits constrained initial binding updates for exact virtual API usernames and namespaces.
- **Pod annotation synchronization:** an opt-in allowance permits selected annotation keys on managed server and helper Job Pods. Pod specifications, ownership, finalizers, and other protected fields remain locked.
- **Terminal Pod cleanup:** the operator can finish deleting already-terminating terminal Pods after verifying ownership, current authority, and stopped containers.
- **Namespace teardown:** provisioner-owned tenant Roles and RoleBindings remain available until cluster and restore finalization finishes.

The synchronization allowances are empty by default. Configure `admissionPolicies.pvcBindingSync.allowedCallers` and `admissionPolicies.podMetadataSync.allowedCallers` using the caller identity, namespaces, and annotation keys observed in denied requests. Equivalent Kustomize overlays are available.

Keep the provisioner running throughout namespace teardown. The change prevents its tenant permissions from disappearing too early; it does not restore permissions already deleted from a terminating namespace.

For cluster deletion, `deletionPolicy: Retain` preserves managed data PVCs and releases cluster owner references from generated recovery Secrets when present. New self-init clusters have no root-token Secret. Namespace deletion removes namespaced resources, so preserve required recovery material before deleting a namespace. `DeleteAll` does not remove external backup objects.

## Backup, storage, and policy changes

- **Bounded retention:** backup retention runs with the successful backup writer’s workload identity. Retention status is separate from snapshot success, and the current snapshot and reserved restore-test snapshot remain protected.
- **Schedule changes:** scheduled backups refresh persisted deadlines when their schedule changes.
- **S3 configuration:** storage targets accept nested S3 options with per-field precedence over existing top-level settings. Omitting the nested fields preserves existing configuration behavior.
- **Storage clients:** backup and restore executors retain configured private CA trust. S3 signing uses credential-Secret regions consistently, and Azure Blob clients accept complete endpoint URLs.
- **Approved-policy reconciliation:** `spec.reconcilePolicies` can repair the operator’s built-in OpenBao policies after an administrator approves the exact contents and grants access. Use the matching release’s signed policy-approval file. Authentication methods, JWT roles, approval policies, and unrelated policies remain administrator-managed.
- **Bootstrap Secret inputs:** raw self-init requests can project selected same-namespace Secret keys, subject to submitter authorization. Bootstrap request references remain immutable.

## Networking, Azure identity, and TLS

Services and advertised addresses support IPv6 and dual-stack clusters. Kubernetes restrictions on changing a Service’s primary IP family still apply.

Cilium installations can configure an operator-owned, namespaced API-server egress allowance through `spec.network.apiServerEgress`. The platform remains responsible for the CNI and cluster-wide policy.

Azure Key Vault seal configuration supports authentication-method selection and direct workload-identity token projection. Azure federation, Key Vault permissions, DNS, and egress remain platform responsibilities.

OpenBao 2.7 uses native reload for mounted TLS certificates. Listener configuration changes still require restarts. Optional hybrid post-quantum TLS key exchange requires OpenBao 2.7 and compatible clients.

Security checks also verify installed admission specifications against embedded release contracts, validate tenant onboarding identities, and require ownership proof before resource mutation. Install matching policies, bindings, RBAC, and manager settings together.

## Upgrade from 0.5.3

1. **Rehearse the production configuration.** Verify current snapshots, independent administrator access, and seal recovery access.
2. **Finish active operations.** Complete backups, retention, restores, restore tests, and OpenBao upgrades. Do not carry an old restore executor across the operator upgrade.
3. **Update cluster-creation templates.** Apply the Target and self-init OIDC requirements to newly created objects. Existing Shared clusters do not require migration merely to upgrade the operator.
4. **Verify and install matching release artifacts.** Apply the 0.6.0 CRDs before upgrading the matching Helm chart. Upgrade policies, RBAC, manager, and helper images together. Review retained Helm values, digest pins, helper overrides, mirrored repositories, and custom installation identities.
5. **Verify actual Pod and helper-image replacement.** Helm readiness alone does not prove that existing Pods contain new helper binaries. BlueGreen voter StatefulSets use `OnDelete`; replace Pods through planned maintenance, one at a time, with quorum and health checks.
6. **Check cluster continuity and monitoring.** Verify readiness, admission health, cluster UIDs, data PVCs, authentication modes, and recovery-material custody.

`OpenBaoCluster.status.restore` is deprecated and no longer written. Use `OpenBaoRestore` status. The `openbao_restore_state` metric adds recovery values 4–7; update alerts that assume the earlier value set.

For older installations, follow the intermediate release migration guidance before this upgrade. Routine operator and OpenBao downgrades remain unsupported.

## Compatibility and validation

Release qualification covers selected combinations of Kubernetes 1.34.3, 1.35.1, and 1.36.1 with OpenBao 2.6.4 and selected OpenBao 2.7.1 scenarios. Validation includes API and admission tests, lifecycle and recovery exercises, and real Azure workload-identity, Key Vault, and Blob operations.

The evidence applies to the tested combinations. It does not qualify every provider, authentication method, seal, storage driver, or topology. Cilium native routing remains unqualified. Rehearse the production combination in staging.

The production BlueGreen policy is unchanged: transitions from pre-2.6 OpenBao to 2.6 or newer remain blocked. Switch a healthy, idle cluster to `RollingUpdate`, wait for the accepted strategy, and then perform that OpenBao upgrade.

Fixes already published in 0.5.2 and 0.5.3 are carried forward and are excluded from the list of new 0.6.0 fixes. This operator release does not automatically update the OpenBao server image.
