# OpenBao Operator 0.6.1

OpenBao Operator 0.6.1 fixes Helm admission-policy serialization, small-cluster Raft Autopilot configuration, and
security issues in go-jose and golang.org/x/net. Restore targets accept stable OpenBao versions from 2.7.0 onward, and
scheduled restore tests can inherit the version recorded with each backup.

## Security update

The operator updates go-jose to 4.1.6 to address an RSA JSON Web Key denial-of-service issue. Install the matching
operator and helper images to keep the release executables and policies consistent.

The release also updates golang.org/x/net to 0.62.0 for
[CVE-2026-78661](https://github.com/advisories/GHSA-75pg-wvh3-34jr). The fix prevents excessive allocations when the
HTML parser coalesces text from crafted input.

## Helm admission policies

The chart preserves CEL expressions when Flux or Kustomize parses and serializes the rendered YAML. Earlier chart
output could acquire newlines in folded expressions and fail the operator's admission-contract verification.
Upgrade the chart, policies, bindings, and operator together. Keep admission protections enabled.

## Raft Autopilot on small clusters

The operator applies Autopilot settings on one- and two-voter Development clusters. When an `autopilot` object is
present and `cleanupDeadServers` is omitted, Kubernetes defaults cleanup to enabled. The operator derives
`minQuorum` as at least three, so OpenBao accepts that configuration. Autopilot does not prune peers below that
minimum. Set `cleanupDeadServers: false` when tuning other Autopilot fields without cleanup on a small cluster.

Rejected Autopilot settings with HTTP status 400 appear in the operator's error logs. Correct the configuration
before retrying.

## Restore versions and scheduled tests

Fresh-target restores accept stable OpenBao releases from 2.7.0 onward, including later minor and major releases.
Prereleases and versions below 2.7.0 remain rejected. Each restore request must pin the exact snapshot source
version; accepting a version does not establish compatibility for every future release, provider, or plugin.

Scheduled restore tests can omit `spec.backup.restoreTest.clusterTemplate.version`. Each generated restore request
then pins the version recorded with its selected backup. An older backup keeps its recorded version after a source
upgrade. An existing version pin continues to require an exact match.

A custom restore image requires a matching version pin. Versions with build metadata, such as `2.7.2+build.1`, also
require an explicit image because `+` is not valid in an image tag.

The operator retains bootstrap, unseal, source identity, exact-version, leadership, ownership, and execution guards.
Scheduled tests supply the snapshot digest from backup metadata. For manual requests, a known digest is checked only
when `source.expectedDigest` is supplied. Scheduled restore tests do not authenticate as application users or read
their secrets. Existing-target restores retain their administrator-controlled recovery procedure.

## OpenBao compatibility

The configured CI and release baseline advances to OpenBao 2.6.5, with 2.7.2 as the current configuration-compatibility
target. Both upstream releases contain security fixes. Review SSH identity-template roles before upgrading the
OpenBao server: wildcard substitutions are rejected by default. The operator release does not update
`spec.version` or automatically upgrade the OpenBao server image.

The [0.6.1 release qualification checks](https://github.com/kubebao/openbao-operator/pull/936/checks) record the full
release profile and the operator upgrade rehearsal from published 0.6.0 to the candidate. Earlier focused results
retain the scope recorded in the compatibility reference. These checks do not qualify every Kubernetes
distribution, network topology, cloud identity, storage driver, or seal provider.

## Upgrade from 0.6.0

1. Finish active backups, retention, restores, restore tests, and OpenBao upgrades. Verify current snapshots,
   independent administrator access, and seal recovery material.
2. After publication, verify the 0.6.1 artifacts, signatures, and provenance.
3. Review retained Helm values, manager digest pins, helper-image overrides, mirrored repositories, and custom
   identities. A complete helper-image override takes precedence over the operator's version-based default.
4. Apply the 0.6.1 CRDs before upgrading the chart.

   ```bash
   kubectl apply -f \
     https://github.com/kubebao/openbao-operator/releases/download/0.6.1/crds.yaml
   ```

5. Upgrade the matching chart, policies, bindings, RBAC, operator, and helper defaults together.

   ```bash
   helm upgrade openbao-operator \
     oci://ghcr.io/kubebao/charts/openbao-operator \
     --version 0.6.1 \
     --namespace openbao-operator-system
   ```

6. Verify the installed operator and the actual init images in managed Pods. Existing Jobs keep their original
   images. BlueGreen voter StatefulSets use `OnDelete`; replace old Pods through planned maintenance, one at a time,
   with quorum and health checks. Chart readiness alone does not prove helper replacement.
7. Verify cluster readiness, admission health, retained data, backup and restore-test status, and authentication.
   Rehearse the production combination in staging before upgrading production.

The Kubernetes API remains `openbao.org/v1alpha1`. The new-cluster Target and self-init requirements from 0.6.0
remain unchanged. Existing Shared objects do not require an authentication migration merely to install this patch.
Routine operator and OpenBao downgrades remain unsupported.

## Prepare for the API-group migration

The published 0.6.1 release is the intended source baseline for the later 0.7.0 migration to `kubebao.org/v1alpha1`.
This patch does not change the API group or transfer resource ownership. Qualify forward migration and rollback
from the published 0.6.1 artifacts to the final 0.7.0 candidate before approving the migration release.
