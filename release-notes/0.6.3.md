# OpenBao Operator 0.6.3

OpenBao Operator 0.6.3 adds Raft catch-up checks between voter replacements and configurable limits for restore snapshot sizes. A returning voter can be Ready while it is still behind the leader; replacing another voter at that point can interrupt writes.

## Rollouts and recovery

The checks cover ordinary Pod-template changes, including startup budgets and resources, managed rolling version upgrades, and rolling retries. The operator waits for the remaining voters to meet Raft health and catch-up checks before advancing. The hold survives a controller restart.

Failed template corrections and rolling retries use a temporary `OnDelete` strategy while the operator repairs voters one at a time. New desired-revision Pods remain intact during startup. The operator restores `RollingUpdate` after the repair completes and fresh Raft health is confirmed. Pending template, version, and replica changes wait for the active rollout.

These checks reduce the risk of replacing another voter before recovery completes. Single-voter and two-voter clusters still require a write outage during replacement. Leader changes can cause brief client errors.

## Restore larger snapshots

Restores keep an 8 GiB limit for each snapshot object by default. Set `spec.source.maxSnapshotSizeBytes` on an `OpenBaoRestore` to select a different limit. Scheduled restore tests use `spec.backup.restoreTest.maxSnapshotSizeBytes`. For example, `17179869184` permits objects up to 16 GiB. Backup status retains size and digest metadata for larger snapshots.

Restore Jobs reserve scratch and ephemeral storage from the selected budget. A 16 GiB budget requests 18151 MiB of ephemeral storage. Check node capacity, namespace quotas, and target PVC capacity before creating the request. Job preparation remains limited to 30 minutes, and the Job deadline remains 40 minutes. Rehearse with representative snapshots and storage throughput.

## Upgrade from 0.6.2

1. Finish active lifecycle operations. Verify a recent backup, a rehearsed restore path, administrator access, and seal recovery material. Install this fix on a settled cluster; it cannot retroactively protect a rollout started by an older operator.
2. If you manage a custom controller identity or policy, grant authenticated read access to `sys/storage/raft/configuration` and `sys/storage/raft/autopilot/state` before upgrading. The default self-init OIDC controller policy already provides these reads. Missing access holds voter rollouts.
3. Apply the 0.6.3 CRDs with server-side apply before upgrading the matching chart, admission policies, RBAC, operator, and helper defaults during a maintenance window. Review retained image pins and helper-image overrides.
4. Verify quorum, Pod readiness, and client behavior. If a rollout stops, inspect `VoterRolloutWaiting` or `RollingPartitionRetry` events, operator logs, controller authentication, and Raft health. Restore access or peer health before continuing. Do not lower the partition manually to bypass the check.

The configurable startup budget introduced in 0.6.2 remains available for slow database opens. This release does not automatically upgrade the separate OpenBao server image.

## API compatibility and migration

The API remains `openbao.org/v1alpha1`. This patch does not perform the API-group migration. Migration from published 0.6.3 artifacts to 0.7.0-rc.2 requires separate qualification and updated guidance before RC.2 publication. The RC.1 migration binary does not accept 0.6.3. Do not upgrade an existing 0.6 installation directly with a 0.7 chart or manifests.
