# OpenBao Operator 0.7.0-rc.2

This release candidate changes the Kubernetes API group from `openbao.org/v1alpha1` to `kubebao.org/v1alpha1` and adds configurable startup budgets for databases that need longer to open. The API version remains `v1alpha1`.

**For staging and evaluation only.** Stable 0.7.0 is not published.

## Changes since RC.1

Set `spec.probes.startup.failureThreshold` to extend the startup window for voters and read replicas. The default remains 60 failures, approximately five minutes. A value of 180 allows approximately 15 minutes; the maximum is 720, approximately one hour. Extended budgets also increase rolling-upgrade readiness and fresh-restore deadlines. Fresh restores and scheduled restore tests accept the same `probes` block in their `clusterTemplate`.

The nominated migration source is 0.6.2, which includes this fix. The previous RC migrates from 0.6.1; its migration binary does not accept the new source version. Installer examples use server-side apply for the larger CRDs.

## Migrate an existing installation

Upgrade the source operator to published **0.6.2** first. Follow the [migration guide for your installation method](https://docs.kubebao.org/next/docs/operate/api-group-migration/) with the **0.7.0-rc.2 migration binary, chart, and images together**. Do not upgrade an existing 0.6 installation directly with a 0.7 chart or manifests; the destination operator does not reconcile `openbao.org` resources.

For affected clusters, pause reconciliation and wait for the pause to be observed before upgrading to 0.6.2. Install the matching CRDs with server-side apply, configure a longer startup budget while paused, then resume during a maintenance window. Rehearse a cold start with representative data and storage. Allow enough migration CLI `--timeout` for the complete sequential rollout.

Finish active lifecycle operations. Verify a recent backup, a rehearsed restore path, administrator access, and seal recovery material. Use one controller replica with admission policies enabled. Keep GitOps controllers and their parents suspended until the guide's hand-back steps are complete.

The migration re-creates custom resources and transfers workload ownership. Custom resource UIDs change. The procedure retains data PVCs, Raft membership, seal material, Service endpoints, and controller authentication. Destination template differences can replace data Pods. Single-voter clusters have downtime; multi-voter clusters can return brief client errors during replacement or leader changes.

Before `commit` starts deleting source resources, `rollback` returns control to 0.6.2 while preserving writes made after migration. Source-resource deletion ends that rollback window. This does not add general operator or OpenBao downgrade support.

## Artifacts and qualification

Verify signed checksums and provenance before use. The migration binary is available for Linux amd64, Linux arm64, and macOS arm64. Intel Macs are unsupported. The operator requires Kubernetes 1.34 or newer; Helm CLI and Flux HelmRelease migrations require Helm 4.

Publication requires release-profile qualification and matching packaged artifacts. The next stable decision also requires the targeted slow-start, rolling-upgrade, restore, migration, and rollback checks and a fresh 48-hour staging soak on this candidate. Earlier RC.1 soak results support unchanged behavior; they do not qualify the new paths.

The [coverage map](https://github.com/kubebao/openbao-operator/blob/0.7.0-rc.2/cmd/api-migration/README.md#configuration-coverage-map) records automated scenarios and remaining environment-specific validation. Kind storage, SoftHSM, and test KMIP fixtures do not qualify production storage, vendor HSMs, cloud KMS, or every Kubernetes distribution. Rehearse the production combination in staging.
