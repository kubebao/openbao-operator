# OpenBao Operator 0.7.0

OpenBao Operator 0.7.0 changes the Kubernetes API group from `openbao.org/v1alpha1` to `kubebao.org/v1alpha1`.
The API version remains `v1alpha1`. The release adds `api-migration` to transfer an existing 0.6.1 installation
while preserving OpenBao data, storage bindings, and controller authentication.

**Release preparation:** 0.7.0 is not published. Final candidate qualification and release-artifact verification
are pending. These notes do not authorize a production migration.

## Breaking change: migrate existing installations

The 0.7 operator serves only the `kubebao.org` API group. A direct Helm upgrade or installation of the 0.7 manifests
leaves existing `openbao.org` resources unmanaged. Changing `apiVersion` in Git does not transfer their ownership.

Upgrade older installations to published **0.6.1** first. Then follow the
[API group migration guide](https://docs.kubebao.org/docs/operate/api-group-migration/) with the **0.7.0** migration
binary, chart, and images. The guide has separate procedures for Helm CLI, kubectl/Kustomize, Flux HelmRelease,
Flux Kustomization, and Argo CD.

Use one controller replica with admission policies enabled. Finish active lifecycle operations, verify a recent
backup, and rehearse the restore path. Review manager, helper, and cluster-level backup-image pins. Keep GitOps
controllers and their parents suspended until the guide's hand-back procedure is complete.

Update custom RBAC, clients, scripts, and inactive Git manifests that reference the old API group. The migration
command creates the new-group resources; do not apply converted OpenBao manifests before `commit` finishes.

## Verification and rollback

The command re-creates custom resources in the new API group and transfers ownership of managed Kubernetes
resources. Custom resource UIDs change. The procedure preserves existing data PVCs, Raft membership, seal material,
Service endpoints, and the controller's OpenBao identity.

Ownership transfer does not restart Pods. After the destination operator starts, differences in its Pod template
can cause a rolling restart. Verification waits for the workload state required by its update strategy. A
single-voter cluster is unavailable during its restart. Multi-voter clusters can also return brief client errors
during Pod replacement or leader changes. Schedule a maintenance window and use clients that handle redirects and
retry operations according to their API semantics.

Before source-resource deletion begins, `rollback` returns control to 0.6.1 while preserving writes made after
migration. `commit` retires the old resources and ends that rollback window when deletion starts. This procedure
does not add general support for operator or OpenBao downgrades.

## Migration binary and prerequisites

The release packages `api-migration` for Linux amd64, Linux arm64, and macOS arm64. Intel Macs are unsupported.
Verify the binary's attestation and signed checksums before use. Each binary accepts only its own destination
release; do not mix a stable binary with an edge chart or images.

The operator requires Kubernetes 1.34 or newer. Helm CLI and Flux HelmRelease migrations require Helm 4 on the
migration host. The operator release does not change `spec.version` or upgrade the OpenBao server automatically.

## Qualification boundary

The configured release profile includes the 0.6.1 operator migration, forward and rollback scenarios, interruption
recovery, security checks, image provenance, and byte reproducibility. Qualification of the final 0.7.0 candidate
is pending; ordinary PR CI and earlier staging runs do not replace it.

The [coverage map](https://github.com/kubebao/openbao-operator/blob/0.7.0/cmd/api-migration/README.md#configuration-coverage-map)
records automated scenarios and remaining environment-specific validation. Kind storage, SoftHSM, and test KMIP
fixtures do not qualify production CSI or RWX storage, vendor HSMs, cloud KMS, workload identity, or every Kubernetes
distribution. Rehearse the exact production combination in staging.
