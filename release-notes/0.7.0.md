# OpenBao Operator 0.7.0

OpenBao Operator 0.7.0 changes the Kubernetes API group from `openbao.org/v1alpha1` to `kubebao.org/v1alpha1`. The API version remains `v1alpha1`. This release includes the API migration command, configurable startup budgets, Raft catch-up checks between voter replacements, larger restore snapshot budgets, and backup recovery fixes.

## Migrate an existing installation

Upgrade the source operator to published **0.6.3** first. Then follow the [migration guide for your installation method](https://docs.kubebao.org/docs/operate/api-group-migration/) with the **0.7.0 migration binary, chart, and images together**. A direct 0.7 chart or manifest upgrade leaves existing `openbao.org` resources unmanaged. Editing `apiVersion` in Git does not transfer ownership.

Finish active lifecycle operations. Verify a recent backup, a rehearsed restore path, administrator access, and seal recovery material. Use one controller replica with admission policies enabled. Keep GitOps controllers and their parents suspended until the guide's hand-back steps are complete.

For databases that need longer to open, configure the startup budget in 0.6.3 before migrating. Pause reconciliation and wait for the pause to be observed before upgrading an affected source installation. Install its CRDs with server-side apply, set the longer budget while paused, and resume during a maintenance window. Rehearse a representative cold start. Supply enough CLI `--timeout` on every `migrate`, `commit`, and `rollback` invocation, including retries, for the complete sequential rollout.

Custom resource UIDs change. Data PVCs, Raft membership, seal material, Service endpoints, and controller authentication are retained. Destination template differences can replace Pods. Single-voter clusters have restart downtime; multi-voter clusters can return brief client errors during replacement or leader changes.

Before `commit` starts deleting source resources, `rollback` returns control to 0.6.3 while preserving later writes. Source-resource deletion ends that rollback window. This does not add general downgrade support.

## Startup and rollout controls

Set `spec.probes.startup.failureThreshold` to extend the startup window for voters and read replicas. The default remains 60 failures, approximately five minutes. A value of 180 allows approximately 15 minutes; the maximum is 720, approximately one hour. Extended budgets also increase the shared rolling-upgrade readiness deadline and fresh-restore deadlines. Fresh restores and scheduled restore tests accept the same `probes` block in `clusterTemplate`.

Voter rollouts wait for authenticated Raft health and catch-up before replacing the next voter. Holds survive controller restarts. Custom controller policies must permit reads of `sys/storage/raft/configuration` and `sys/storage/raft/autopilot/state`; the default self-init OIDC policy already grants these reads.

Operator-managed OpenBao server upgrades from versions before 2.6 to 2.6 or newer are blocked for both `RollingUpdate` and `BlueGreen`. The operator does not yet provide a qualified rollout order across this protocol boundary. API-group migration that retains the server version is unaffected.

## Restore and backup recovery

Restores keep the 8 GiB snapshot-object limit by default. Set `spec.source.maxSnapshotSizeBytes` on a restore request, or `spec.backup.restoreTest.maxSnapshotSizeBytes` for scheduled restore tests, to select a larger budget. The budget also reserves scratch and ephemeral storage. It does not extend the 30-minute preparation deadline or 40-minute Job deadline. Rehearse with representative data, throughput, and destination capacity.

Backup attempt receipts let the operator recover manual and scheduled attempts after a controller restart while the owned Job and matching operation lock remain available. When Job creation has an uncertain outcome, the operator retains the operation lock instead of submitting another backup. If the named Job remains absent, inspect the lock, backup status, and object storage, then contact the maintainers before changing status or retrying.

## Requirements and verification

Kubernetes 1.34 or newer is required. Helm CLI and Flux HelmRelease migrations require Helm 4. Migration binaries cover Linux amd64, Linux arm64, and macOS arm64; Intel Macs are unsupported. Verify signed checksums and provenance before use.

The operator release does not upgrade the separate OpenBao server image. The [coverage map](https://github.com/kubebao/openbao-operator/blob/0.7.0/cmd/api-migration/README.md#configuration-coverage-map) records automated scenarios and remaining environment-specific validation. Rehearse the exact production combination; Kind storage, SoftHSM, and test KMIP fixtures do not qualify production storage, vendor HSMs, cloud KMS, or every Kubernetes distribution.
