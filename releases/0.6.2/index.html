OpenBao Operator 0.6.2

Configurable startup budgets for slow database opens and matching lifecycle deadlines.

Updated 16 November 2026 · 2 min read

On this page
  • Configure the startup budget
  • Upgrade from 0.6.1
  • Qualification and migration

OpenBao Operator 0.6.2 adds a configurable startup probe budget for databases that need longer to open. Extended budgets also increase rolling-upgrade readiness and fresh-restore deadlines. The operator and helper builds use Go 1.27.4.

Configure the startup budget

Set spec.probes.startup.failureThreshold to allow more consecutive probe failures. The default remains 60, approximately five minutes. A value of 180 allows approximately 15 minutes; the maximum is 720, approximately one hour. The setting applies to voters and read replicas. Fresh restores and scheduled restore tests accept the same setting in their clusterTemplate.

Read Allow more time for database startup before changing the budget. Rehearse a cold start with representative data and storage; database size alone does not predict startup time.

Upgrade from 0.6.1

Finish active lifecycle operations. Verify a recent backup, a rehearsed restore path, administrator access, and seal recovery material. For affected clusters, pause reconciliation and wait for the operator to observe the pause before upgrading.

Apply the 0.6.2 CRDs with server-side apply before upgrading the matching chart, admission policies, RBAC, operator, and helper defaults. Configure the longer budget while affected clusters remain paused, then resume during a maintenance window. Verify quorum, Pod readiness, and client behavior.

Changing the budget updates the Pod template and can replace Pods. A Pod already in a startup-probe restart loop can prevent the StatefulSet from applying the new template. The storage guide describes the required checks before authorized maintenance. Retain the PVC, and use the no-leader recovery procedure if quorum is unavailable.

Review the complete 0.6.2 release notes. After publication, obtain the release assets and the chart at oci://ghcr.io/kubebao/charts/openbao-operator, version 0.6.2.

Qualification and migration

The release PR tracks publication and release-profile qualification, including the operator upgrade from published 0.6.1. Qualification must pass before publication. Ordinary PR CI does not replace release-profile qualification or an environment-specific staging rehearsal.

The Kubernetes API remains openbao.org/v1alpha1. This patch does not perform the API-group migration or automatically upgrade the OpenBao server. Migration from published 0.6.2 artifacts to the next 0.7 candidate requires separate qualification and updated migration guidance before stable 0.7.0.

OpenBao Operator is an independent open source project.
