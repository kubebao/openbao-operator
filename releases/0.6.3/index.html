OpenBao Operator 0.6.3

Raft catch-up checks, guarded rollout recovery, and configurable restore snapshot limits.

Updated 18 November 2026 · 3 min read

On this page

OpenBao Operator 0.6.3 checks Raft catch-up between voter replacements. A returning voter can be Ready while still behind the leader. Replacing another voter before recovery completes can interrupt writes.

Restore requests and scheduled restore tests can also select a larger snapshot size budget while retaining the 8 GiB default.

Voter rollouts and recovery

The operator checks the remaining voters before advancing ordinary Pod-template changes, managed rolling version upgrades, and rolling retries. The hold survives a controller restart. Failed corrections and rolling retries use a temporary OnDelete strategy while the operator repairs voters one at a time. It restores RollingUpdate after repair and fresh Raft health checks complete.

Read Wait for Raft catch-up between voter replacements for controller permissions, progress events, and recovery boundaries. Single-voter and two-voter clusters still require a write outage during replacement. Leader changes can cause brief client errors.

Restore larger snapshots

Set spec.source.maxSnapshotSizeBytes on an OpenBaoRestore, or spec.backup.restoreTest.maxSnapshotSizeBytes for scheduled restore tests. For example, 17179869184 permits snapshot objects up to 16 GiB. The limit applies to the downloaded object. Backup status retains size and digest metadata for larger snapshots.

The restore Job reserves scratch and ephemeral storage from the selected budget. A 16 GiB budget requests 18151 MiB of ephemeral storage. Check node capacity, namespace quotas, and target PVC capacity. Job preparation remains limited to 30 minutes, and the Job deadline remains 40 minutes. Rehearse with representative snapshots and storage throughput. See Restore larger snapshots.

Upgrade from 0.6.2

Finish active lifecycle operations. Verify a current backup, a rehearsed restore path, administrator access, and seal recovery material. Install this fix on a settled cluster; it cannot protect a rollout already started by an older operator.

Custom controller identities need authenticated read access to sys/storage/raft/configuration and sys/storage/raft/autopilot/state. The default self-init OIDC controller policy already grants these reads. Missing access holds voter rollouts.

Apply the 0.6.3 CRDs with server-side apply before upgrading the matching chart, policies, RBAC, operator, and helper defaults during a maintenance window. Follow Upgrade the operator. Verify quorum, Pod readiness, and client behavior. Keep the existing startup budget for databases that need longer to open. Upgrade the separate OpenBao server image only when you intend to change its version.

Obtain the 0.6.3 release assets and the chart at oci://ghcr.io/kubebao/charts/openbao-operator, version 0.6.3. The handwritten notes are at release-notes/0.6.3.md.

Qualification and API migration

The release PR tracks the required release-profile qualification, including an operator upgrade from published 0.6.2. Earlier code-candidate tests do not replace this qualification or a rehearsal with production data and storage.

The API remains openbao.org/v1alpha1. Migration from published 0.6.3 artifacts to 0.7.0-rc.2 requires separate qualification and updated guidance before RC.2 is published. The RC.1 migration binary does not accept 0.6.3. A direct 0.7 chart or manifest upgrade leaves existing openbao.org resources unmanaged.

OpenBao Operator is an independent open source project.
