Release preparation draft. Version 0.6.0 is not published. Final runtime, cloud,
performance, and distribution qualification remains pending.

OpenBao Operator 0.6.0 adds target-specific controller JWTs, guarded restore
recovery, operator-created restore targets, scheduled restore tests, and
administrator-approved policy reconciliation. Networking adds IPv6 and
dual-stack Services and a scoped Cilium API-server allowance. Azure Key Vault
seal configuration can project a workload-identity token directly.

## Review the new-cluster contract

Every new Development or Hardened `OpenBaoCluster` must declare
`spec.controllerJWTMode: Target`, enable self-init and self-init OIDC, and provide
a non-empty self-init request list. Configure an independent administrator login
before creation. OpenBao revokes its bootstrap root token, and the operator does
not create a root-token Secret for this path.

Existing objects with an omitted mode or `Shared` retain Shared behavior on
reads and ordinary updates. The CRD does not default the field. Deleting and
recreating an object uses the new CREATE requirements and gives it a new UID.

[Controller JWT configuration](../../docs/operate/controller-jwt-mode/) explains
the admission contract. [Migration](../../docs/operate/controller-jwt-migration/)
is optional and changes the same object in place. An administrator must prepare
and verify the existing role before selecting Target, preserve its restrictions,
then remove shared trust and test rejection. The change is one-way. The operator
does not migrate roles or fall back to a shared JWT or root token.

## Plan restore authority and recovery

An accepted `OpenBaoRestore` authorizes one execution of immutable intent.
Revoking the submitter's permission does not cancel it. Delete the request before
execution commitment to cancel accepted work; after commitment, follow its
recorded recovery state. A committed snapshot submission is never retried.

A restore into an existing cluster ends `Unknown` after submission and retains
a management hold. The hold does not fence processes or stop application traffic.
An administrator inspects the restored data and trust, then acknowledges
`Resume` for a managed restart or `Abandon` for manual responsibility. An
existing-target request remains `Unknown` after management resumes.

New restore targets support retained and disposable single-voter workflows on
the supported OpenBao 2.7 template versions. Scheduled restore tests use
disposable targets within one Kubernetes cluster. Neither mechanism adopts
existing resources or proves cross-version restore compatibility.

Snapshots can restore older JWT role trust. Preserve a usable administrator
login in the restored state and repair destination audiences independently.
[Restore authentication](../../docs/operate/restore/authentication/) and
[uncertain-restore recovery](../../docs/operate/restore/recover-uncertain/)
describe the operational boundary.

## Upgrade from 0.5.3

Finish active backups, restores, restore tests, retention, and OpenBao upgrades.
Take and verify current snapshots. Review the complete
[0.6.0 release notes](https://github.com/kubebao/openbao-operator/blob/0.6.0/release-notes/0.6.0.md)
before changing CRDs or installation resources. That tag link becomes available
with publication; this draft does not identify a published release.

After publication and artifact verification, apply the 0.6.0 CRDs before the
matching chart upgrade. Upgrade policies, RBAC, manager, and helper images
together. Review Helm `--reuse-values`, old digest pins, helper overrides,
custom identities, namespace label ownership, and admission caller maps.

Update cluster factories and GitOps templates before they create new objects.
Existing Shared objects do not need a migration merely to update the operator.
Review `OpenBaoRestore` status and alerts: `OpenBaoCluster.status.restore` is no
longer written, and `openbao_restore_state` includes recovery values 4–7.

Verify the init image installed in every OpenBao Pod. Helm readiness does not
prove that existing Pods contain new helper binaries. Replace old Pods through
[planned maintenance](../../docs/operate/maintenance/), one at a time with quorum
and health checks. BlueGreen voter StatefulSets use `OnDelete`.

`deletionPolicy: Retain` preserves data PVCs and generated bootstrap Secrets when
present, after releasing their cluster owner references. New self-init clusters
have no root-token Secret. Retained material remains sensitive; referenced
credentials follow their own ownership policy. External snapshots survive
`DeleteAll`.

## Preserve the support boundary

The configured release matrix uses Kubernetes 1.34.3, 1.35.1, and 1.36.1. Final
0.6.0 qualification and publication are pending. A configured matrix is not proof
that every distribution, cloud identity, seal, storage driver, or topology passed.
Review [compatibility](../../docs/reference/compatibility/) and rehearse the exact
production combination.

Cilium native routing remains unqualified. VXLAN qualification does not extend
to native routing. Cloud integration and performance claims require their own
current-candidate evidence.

The production BlueGreen policy is unchanged: pre-2.6 to 2.6-or-newer transitions
remain blocked. Use the documented idle switch to `RollingUpdate` before that
OpenBao upgrade. Upstream forwarding changes do not establish mixed-version or
datastore downgrade safety. Routine operator and workload downgrades remain
unsupported.

The release carries forward 0.5.2 backup, PVC, and restore safety fixes and the
0.5.3 Go certificate protections. These were already available in the 0.5 line.
The operator release does not update the separate OpenBao server image.
