OpenBao Operator 0.6.1 fixes Helm admission-policy serialization and small-cluster
Raft Autopilot configuration. It also addresses denial-of-service issues in
go-jose and golang.org/x/net. Restore targets accept stable OpenBao versions from
2.7.0 onward, and scheduled tests can inherit each backup's recorded version.

## Review the fixes

- The Helm chart preserves CEL expressions through Flux and Kustomize YAML
  serialization, so added newlines do not change the admission contract.
- One- and two-voter Development clusters receive valid Autopilot settings.
  Cleanup derives a minimum quorum of three; peers are not pruned below it.
- The operator and helpers update go-jose to 4.1.6 for the RSA JSON Web Key
  denial-of-service fix and golang.org/x/net to 0.62.0 for
  [CVE-2026-78661](https://github.com/advisories/GHSA-75pg-wvh3-34jr) in the HTML parser.
- The configured OpenBao validation baseline advances to 2.6.5, with 2.7.2 as the
  current configuration-compatibility target. Installing the operator does not
  upgrade the separate OpenBao server image.

## Configure restore versions

A fresh target must use the exact snapshot source version. Stable versions from
2.7.0 onward are accepted; prereleases and older versions remain rejected.
Admission acceptance does not qualify every future release or provider.

For scheduled restore tests, omit
`spec.backup.restoreTest.clusterTemplate.version` to inherit each backup's
recorded version. Each request freezes that version before execution. A custom
image requires a matching version pin. Build metadata also requires an explicit
image because `+` cannot appear in a container image tag.

[Restore version support](../../docs/reference/compatibility/#restore-version-support),
[new targets](../../docs/operate/restore/new-cluster/), and
[scheduled tests](../../docs/operate/restore/tests/) describe the checks and
recovery requirements. Existing-target restores retain administrator-controlled
recovery.

## Upgrade from 0.6.0

Finish active operations and verify current snapshots, administrator access, and
seal recovery material. After publication, verify the release signatures and
provenance, then apply the 0.6.1 CRDs before upgrading the matching chart.
Install matching policies, bindings, RBAC, operator, and helper defaults.

Review retained Helm values, manager digest pins, complete helper-image
overrides, mirrored repositories, and custom identities. Verify actual init
images in managed Pods. Existing Jobs keep their original images, and
BlueGreen voter StatefulSets use `OnDelete`. Replace old Pods through
[planned maintenance](../../docs/operate/maintenance/), with quorum and health
checks. Chart readiness alone does not prove helper replacement.

Review the complete
[0.6.1 release notes](https://github.com/kubebao/openbao-operator/blob/0.6.1/release-notes/0.6.1.md)
before upgrading. After publication, obtain the
[release assets](https://github.com/kubebao/openbao-operator/releases/tag/0.6.1)
and the chart at `oci://ghcr.io/kubebao/charts/openbao-operator`, version `0.6.1`.

## Preserve the qualification boundary

The [0.6.1 release qualification checks](https://github.com/kubebao/openbao-operator/pull/936/checks)
record the full release profile and the operator upgrade rehearsal from published
0.6.0 to the candidate. Earlier focused checks retain the scope recorded in
[compatibility](../../docs/reference/compatibility/). Rehearse the
production combination in staging. Routine operator and OpenBao downgrades
remain unsupported.

The API remains `openbao.org/v1alpha1`. Published 0.6.1 is the intended source
baseline for the later 0.7.0 API-group migration. This patch does not change the
API group or transfer resource ownership. Forward and rollback migration
qualification must use the published 0.6.1 artifacts and final 0.7.0 candidate
before the migration release is approved.
