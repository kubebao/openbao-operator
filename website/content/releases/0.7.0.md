OpenBao Operator 0.7.0 moves the Kubernetes API group from `openbao.org/v1alpha1` to `kubebao.org/v1alpha1`.
The API version remains `v1alpha1`. The migration command transfers workload ownership while preserving existing
OpenBao data, storage, and controller authentication.

## Migrate from 0.6.3

{{< callout type="warning" title="Do not upgrade an existing installation directly" >}}
The 0.7 operator does not reconcile `openbao.org` resources. A direct Helm upgrade or application of the 0.7
installer leaves those resources unmanaged. Editing `apiVersion` in Git does not transfer workload ownership.
{{< /callout >}}

Upgrade older installations to published 0.6.3 first. Then follow the
[API group migration](../../docs/operate/api-group-migration/) for the installation method. The overview links
to procedures for Helm CLI, kubectl/Kustomize, Flux HelmRelease, Flux Kustomization, and Argo CD.

Use one controller replica, keep admission policies enabled, finish active operations, and verify a recent backup
with a rehearsed restore path. Review helper-image pins and keep GitOps controllers suspended through hand-back.
Use the destination release's matching binary, chart, and images.

If a database needs longer to open, configure its startup budget in 0.6.3 before migration. Follow the pause and
maintenance steps in [Allow more time for database startup](../../docs/configure/storage/#allow-more-time-for-database-startup).
Supply enough CLI `--timeout` on every rollout command and resumed invocation for the complete sequential rollout.

## Configure startup and restore budgets

`spec.probes.startup.failureThreshold` accepts 60 to 720 failures. The default 60 permits approximately five minutes;
180 permits approximately 15 minutes. The setting applies to voters and read replicas. Extended budgets also
increase the shared rolling-upgrade readiness deadline and fresh-restore deadlines. Fresh restores and scheduled
restore tests accept the same `probes` block in `clusterTemplate`.

Restores keep the 8 GiB snapshot-object limit by default. Set `spec.source.maxSnapshotSizeBytes`, or
`spec.backup.restoreTest.maxSnapshotSizeBytes` for scheduled tests, to select a larger budget. The Job reserves
scratch and ephemeral storage from that budget. The 30-minute preparation and 40-minute Job deadlines remain
unchanged. Rehearse representative data, throughput, and destination capacity.

## Check voter and backup recovery

Voter rollouts wait for authenticated Raft health and catch-up between replacements. Holds survive controller
restarts. Custom controller policies must permit reads of `sys/storage/raft/configuration` and
`sys/storage/raft/autopilot/state`; the default self-init OIDC controller policy already grants them.

Backup attempt receipts recover manual and scheduled attempts across controller restarts while the owned Job and
matching operation lock remain available. An uncertain Job submission keeps the backup operation lock.
Inspect the named Job, status, and object storage before retrying;
contact the maintainers when the Job remains absent. See [Trigger and verify a backup](../../docs/operate/backups/#trigger-and-verify-a-backup).

## Plan availability and rollback

Custom resource UIDs change, but existing data PVCs, Raft membership, seal material, Service endpoints, and the
controller's OpenBao identity remain in place. Ownership transfer does not restart Pods. The destination operator
can then roll Pods to its template, and verification waits for the state required by the update strategy.

Single-voter clusters have restart downtime. Multi-voter clusters can also return brief client errors during Pod
replacement and leader changes. Read the guide's [availability guidance](../../docs/operate/api-group-migration/#plan-for-availability)
before scheduling the migration.

`rollback` can return control to 0.6.3 until `commit` begins deleting source resources. It preserves writes made
after migration. Source-resource deletion ends that rollback window. Routine downgrades remain unsupported.

{{< callout type="warning" title="OpenBao upgrades across the 2.6 boundary are blocked" >}}
The operator rejects server upgrades from versions before 2.6 to 2.6 or newer for both `RollingUpdate` and
`BlueGreen`. It does not yet provide a qualified rollout order across this protocol boundary. API-group migration
that retains the server version is unaffected.
{{< /callout >}}

## Verify the release artifacts

Obtain the [0.7.0 release assets](https://github.com/kubebao/openbao-operator/releases/tag/0.7.0)
and chart version `0.7.0` at `oci://ghcr.io/kubebao/charts/openbao-operator`.
Review the [complete release notes](https://github.com/kubebao/openbao-operator/blob/0.7.0/release-notes/0.7.0.md)
and verify signatures, attestations, and checksums before use.

The migration binary platforms are Linux amd64, Linux arm64, and macOS arm64. Intel Macs are unsupported.
The operator requires Kubernetes 1.34 or newer. Helm CLI and Flux HelmRelease migrations require Helm 4 on the
migration host. Installing the operator does not upgrade the separate OpenBao server image.

## Preserve the qualification boundary

The [release lifecycle](../../docs/reference/release-lifecycle/#stable-release-gates) defines the stable release gates.
The release workflow requires a passed release-profile qualification and matching image digests and payload bytes
before publication. Inspect `provenance-index.json` for the source tag, artifact digests, and publisher identities.
The release PR checks record candidate qualification. Earlier staging and Nightly results retain their stated scope.

The [coverage map](https://github.com/kubebao/openbao-operator/blob/0.7.0/cmd/api-migration/README.md#configuration-coverage-map)
separates automated scenarios from remaining environment-specific validation. Rehearse the exact production
combination. Local storage, SoftHSM, and test KMIP fixtures do not qualify production storage, vendor HSMs, cloud KMS,
workload identity, or every Kubernetes distribution.
