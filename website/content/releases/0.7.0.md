OpenBao Operator 0.7.0 moves the Kubernetes API group from `openbao.org/v1alpha1` to `kubebao.org/v1alpha1`.
The API version remains `v1alpha1`. The migration command transfers workload ownership while preserving existing
OpenBao data, storage, and controller authentication.

{{< callout type="note" title="Release preparation" >}}
0.7.0 is not published. Final candidate qualification and release-artifact verification are pending.
The latest published release remains [0.6.1](../0.6.1/). This page does not record a qualified release.
{{< /callout >}}

## Migrate from 0.6.1

{{< callout type="warning" title="Do not upgrade an existing installation directly" >}}
The 0.7 operator does not reconcile `openbao.org` resources. A direct Helm upgrade or application of the 0.7
installer leaves those resources unmanaged. Editing `apiVersion` in Git does not transfer workload ownership.
{{< /callout >}}

Upgrade older installations to published 0.6.1 first. Then follow the
[API group migration](../../docs/operate/api-group-migration/) for the installation method. The overview links
to procedures for Helm CLI, kubectl/Kustomize, Flux HelmRelease, Flux Kustomization, and Argo CD.

Use one controller replica, keep admission policies enabled, finish active operations, and verify a recent backup
with a rehearsed restore path. Review helper-image pins and keep GitOps controllers suspended through hand-back.
Use the destination release's matching binary, chart, and images.

## Plan availability and rollback

Custom resource UIDs change, but existing data PVCs, Raft membership, seal material, Service endpoints, and the
controller's OpenBao identity remain in place. Ownership transfer does not restart Pods. The destination operator
can then roll Pods to its template, and verification waits for the state required by the update strategy.

Single-voter clusters have restart downtime. Multi-voter clusters can also return brief client errors during Pod
replacement and leader changes. Read the guide's [availability guidance](../../docs/operate/api-group-migration/#plan-for-availability)
before scheduling the migration.

`rollback` can return control to 0.6.1 until `commit` begins deleting source resources. It preserves writes made
after migration. Source-resource deletion ends that rollback window. Routine downgrades remain unsupported.

## Verify the release artifacts

After publication, obtain the [0.7.0 release assets](https://github.com/kubebao/openbao-operator/releases/tag/0.7.0)
and chart version `0.7.0` at `oci://ghcr.io/kubebao/charts/openbao-operator`.
Review the [complete release notes](https://github.com/kubebao/openbao-operator/blob/0.7.0/release-notes/0.7.0.md)
and verify signatures, attestations, and checksums before use.

The migration binary platforms are Linux amd64, Linux arm64, and macOS arm64. Intel Macs are unsupported.
The operator requires Kubernetes 1.34 or newer. Helm CLI and Flux HelmRelease migrations require Helm 4 on the
migration host. Installing the operator does not upgrade the separate OpenBao server image.

## Preserve the qualification boundary

The [release PR](https://github.com/kubebao/openbao-operator/pull/948) tracks final qualification. At this preparation
stage, its full release candidate has not been qualified. Earlier staging and Nightly results do not establish
that the final release payloads passed.

The [coverage map](https://github.com/kubebao/openbao-operator/blob/0.7.0/cmd/api-migration/README.md#configuration-coverage-map)
separates automated scenarios from remaining environment-specific validation. Rehearse the exact production
combination. Local storage, SoftHSM, and test KMIP fixtures do not qualify production storage, vendor HSMs, cloud KMS,
workload identity, or every Kubernetes distribution.
